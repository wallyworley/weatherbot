# Fix plan — 2026-05-28 (revised, lean version)

**Supersedes** the earlier 10-step version of this file.

## Problem (one paragraph)

`parse_cli` in `data/nws_text_products.py` uses `\bTODAY\b` as a word-boundary token match. In the evening intraday CLI bodies issued by some WFOs (KEWX, KBOU, KFWD, KMPX), the header line contains "VALID TODAY AS OF HH:MM PM LOCAL TIME". The regex matches that occurrence first, captures the chunk between it and the next `TODAY` (the actual section header), and that chunk has no `MAXIMUM` line. The parser returns `None`, and the outer `_select_cli_for_target` silently falls through to an earlier, less-complete intraday CLI. Result: `cli_obs.tmax_f` for some 5/27 station-dates is the high recorded as-of an earlier afternoon snapshot, not the actual daytime max. The reviewer found four such rows and showed they would mis-settle two still-open paper fills (id 381, 420) when settle fires at 14:23 UTC.

## Success criterion

After the work below, this query returns zero rows on integer-comparable cases:

```sql
SELECT km.station, km.valid_date, co.tmax_f as our_cli,
       NULLIF(km.payload->>'expiration_value','')::float as kalshi
FROM kalshi_market km
LEFT JOIN cli_obs co ON co.station=km.station AND co.local_date=km.valid_date
WHERE NULLIF(km.payload->>'expiration_value','') IS NOT NULL
  AND co.tmax_f IS NOT NULL AND km.valid_date >= '2026-05-20'
GROUP BY km.station, km.valid_date, co.tmax_f, km.payload->>'expiration_value'
HAVING co.tmax_f != NULLIF(km.payload->>'expiration_value','')::float;
```

(Days where Kalshi peaked after the last NWS issuance are accepted; we'll annotate any remaining rows.)

### Step 5 — Fix the regex, anchored on `MAXIMUM`

The robust anchor is not the section header — it's the `MAXIMUM` data line itself. Walk backward from a `MAXIMUM` match to find the nearest preceding `TODAY` or `YESTERDAY` token on its own indented line. That structurally cannot mismatch on "VALID TODAY".

Pseudocode:
```python
def parse_cli(text):
    out = CliObservation(None, None, None, None, None)
    # Find all section headers (header line = whitespace + WORD + whitespace EOL)
    headers = [(m.start(), m.group(1).upper())
               for m in re.finditer(
                   r"^\s+(YESTERDAY|TODAY|MONTH TO DATE|SINCE)\s*$",
                   text, re.MULTILINE | re.IGNORECASE)]
    # For each MAXIMUM/MINIMUM line, attribute it to the nearest preceding
    # YESTERDAY or TODAY header.
    for label_pref in ("YESTERDAY", "TODAY"):
        m_max = _max_for_section(text, headers, label_pref)
        m_min = _min_for_section(text, headers, label_pref)
        if m_max or m_min:
            out.section = label_pref
            if m_max: out.tmax_f, out.tmax_time_lst = float(m_max[0]), m_max[1]
            if m_min: out.tmin_f, out.tmin_time_lst = float(m_min[0]), m_min[1]
            break
    return out
```

The `_max_for_section`/`_min_for_section` helpers iterate all `_CLI_MAX`/`_CLI_MIN` matches in the text, look up the nearest preceding header position, and only return matches whose attributed header equals the requested label.

**Also in Step 5**: loosen `_select_cli_for_target` to accept YESTERDAY whenever it parses, regardless of `for_date`. Evidence found during fixture capture: KNYC's morning-after CLI (`9dcfff41...`, issued 5/27 06:22 UTC) has `CLIMATE SUMMARY FOR MAY 26 2026` in the title with a valid YESTERDAY section. My current code rejects this because `for_date != target+1`. We currently get the right value for KNYC by accident (the 5/26 evening TODAY CLI catches the peak first). The fix is safe because YESTERDAY by definition reports yesterday's data; the `for_date` check was unnecessary defense.
