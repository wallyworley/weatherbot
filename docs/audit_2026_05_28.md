## 4. Changes by area

### 4.1 CLI parser rewrite (`data/nws_text_products.py`, commit bb6d042)

**Claim**: KEWX (Austin/SAT) and KBOU (Denver) don't issue a `YESTERDAY` section in their morning CLI, so the previous fetcher was reading the `TODAY` section of the early-morning CLI — which only contained the overnight low (logged as `MAXIMUM` at 3am because no daytime data had been recorded yet).

**Specific evidence I used**:
- Raw CLI text for `KAUS 2026-05-26` fetched from NWS shows `CLIMATE SUMMARY FOR MAY 27 2026 ... VALID AS OF 0700 AM LOCAL TIME` with `MAXIMUM 65 3:42 AM`.
- METAR daily max for KAUS 2026-05-26 was 88°F (queried directly).
- Kalshi `KXHIGHAUS-26MAY26` settled at `expiration_value=88.00` per public API.

**What the fix does**:
1. Widens NWS product window from `target+1 00:00 → target+1 18:00 UTC` to `target 18:00 UTC → target+2 00:00 UTC`.
2. Parses the `CLIMATE SUMMARY FOR <date>` line.
3. Walks products newest-first, returns the first one where either:
   - `for_date == target+1` AND `section == 'YESTERDAY'` AND `tmax_f` is set, OR
   - `for_date == target` AND `section == 'TODAY'` AND `tmax_f` is set AND `tmax_time_lst` contains `PM`.

**What could be wrong**:
- The "prefer YESTERDAY" priority is implicit in the newest-first ordering, but if the next-morning CLI's YESTERDAY section has been corrected/updated *later* than the same-day evening TODAY CLI, we'd accept the evening TODAY first and skip the more authoritative next-morning YESTERDAY. **Verify**: for any station that has both a `for_date==target` PM-TODAY CLI AND a `for_date==target+1` YESTERDAY CLI, which one is closer to Kalshi's `expiration_value`?
- The `_is_pm_time` heuristic (`"PM" in tmax_time_lst.upper()`) is naive. If a WFO ever writes the time as "12:30" without AM/PM, it would not match. Probably fine for current data but a future-proofing concern.
- The window starts at `target 18:00 UTC` (1pm CDT). For Pacific-time stations that means 11am PT, before their afternoon high. We rely on the morning-after CLI capturing those.

### 4.2 Backfill of `cli_obs` for last 14 days

Ran `python -m weather_bot.jobs.pull_cli --days-back 14` on VPS, which overwrote `cli_obs` rows for all 21 stations × 14 days. Output reports "captured 284 CLI rows across 21 stations".

**What could be wrong**:

- We have no audit trail of the *previous* `tmax_f` values for the overwritten days. Only the most recent reading per `(station, local_date)` is retained.
- For 10 days, our backfilled `cli_obs.tmax_f` still disagrees with Kalshi by 1-2°F. Audit log of disagreements is in chat history; reproducible via the audit query in §3.2.

### 4.3 `jobs/settle_paper_fills.py` change (commit 3ae1fb5)

**Before**: prefer CLI; if CLI absent, fall back to METAR-derived `daily_obs.tmax_f`.

**After**: CLI only. If CLI absent, return `None`, fill stays unsettled, will retry next day.

**Rationale**: METAR daily max undercounts CLI by 0.5-1°F per memory file `measured_findings_2026-05-01.md`. On boundary buckets (CLI exactly equals an edge value), the 1°F gap flips the outcome.

**What could be wrong**:
- The fix means fills can stay unsettled for >1 day if CLI fetch fails. The dashboard may show "Open" for fills that should have closed.
- There's a race: if the `weatherbot-cli.timer` (13:23 UTC daily) fails or is delayed, the `weatherbot-settle.timer` (14:23 UTC daily) will defer everything. Was anything assumed to fire that now won't?
- No backstop: if NWS CLI for a station disappears entirely, the fill is stuck forever. Probably acceptable for paper mode but worth flagging.

### 4.4 Dashboard timezone changes (commits fcb256a and 1ed2506)

The VPS clock is UTC. At 8pm ET (midnight UTC), `CURRENT_DATE` in Postgres and `datetime.now()` in Python both return tomorrow. This caused the dashboard's "Today" page to show tomorrow's date and report empty results.

**What changed**:
- `app_v2.py` now imports `ZoneInfo("America/New_York")` and defines `_et_now()`.
- Every SQL `CURRENT_DATE` referring to "today's markets" was replaced with `(now() AT TIME ZONE 'America/New_York')::date`.
- `observed_high_today` now compares `(m.obs_time AT TIME ZONE st.tz)::date = (now() AT TIME ZONE st.tz)::date` (station-local today, not ET today).
- Page header now displays `"Thursday, May 28, 2026 · ET"`.

**What could be wrong** *(important — this is the most likely source of the dashboard issue the user is seeing)*:
- The user is in ET. The `kalshi_market.valid_date` is the station-local date. For KSFO market `26MAY27`, valid_date is `2026-05-27` (which is May 27 in Pacific local time = May 27 in ET as well). For most US stations valid_date will match the user's ET date 1:1, but at the boundary it may not.
- At 8pm ET on May 27, the dashboard now correctly shows "Today = May 27". But all KSFO 5/27 markets *close* at midnight PT (3am ET on 5/28). At 8pm ET, KSFO markets are still open. Trades placed at 8pm ET on KSFO 5/27 markets will have `valid_date=2026-05-27` — matches the new ET filter. ✓
- However: at 11pm ET on May 27 (about 3 hours from now), KSFO markets are still open (8pm PT). But at 1am ET on May 28, ET-today is 5/28, while KSFO markets for 5/27 are still live until 12am PT (3am ET). The dashboard would say "Today is May 28" and not show KSFO 5/27 trades. **Verify what the user is seeing right now and at what local time.**
- The Engine Room queries `prob_forecast.valid_date = (now() AT TIME ZONE 'America/New_York')::date` and `kalshi_market.valid_date = (now() AT TIME ZONE 'America/New_York')::date`. If NBM hasn't issued tomorrow's forecast yet at this hour, the Engine Room may show empty.

### 4.5 Kalshi expiration_value cross-check display (commit f3d17f7 + 42d5f18)

- Added `NULLIF(km.payload->>'expiration_value','')::float AS kalshi_settle_f` to `_v2_settled_fills` SELECT list.
- Trade row template appends `"(Kalshi settled at X°F)"` when `kalshi_settle_f` differs from `cli_tmax_f` by ≥0.5°F.
- Initial commit f3d17f7 used a bare `::float` cast which crashed with `invalid input syntax for type double precision: ""` on unsettled markets that have an empty-string `expiration_value`. 42d5f18 wrapped it in NULLIF.

**What could be wrong**:
- The `kalshi_market.payload->>'expiration_value'` is only populated after we pull settled markets. The one-off pull I ran today fetched 3600 markets, but events older than ~30 settled events per series were skipped. Some historical events may not have settlement data.
- The daily timer `weatherbot-kalshi-settled.timer` was set to fire at 15:00 UTC, which is *after* `weatherbot-settle.timer` at 14:23 UTC. This means settle still uses cli_obs, not Kalshi expiration_value. If the user expected settle to use Kalshi's value, it does not.
- Display threshold of 0.5°F is arbitrary. Kalshi values are integer; CLI values are integer; the difference is always 0 or ≥1. The 0.5 threshold is unnecessary precision.

## 6. Honest list of things I'm least confident about

In rough order of "most likely to be wrong":

1. **The 28-fill bulk UPDATE.** I trusted `cli_obs` to be the ground truth, but `cli_obs` had just been overwritten by the new parser earlier the same day. If the parser sometimes picks the *wrong* issuance (e.g., the 2pm intraday TODAY when a later evening or next-morning final exists), the UPDATE used a wrong number. The §3.2 audit query is the test.

2. **The dashboard "Today" filter in ET.** Cross-time-zone boundary cases (Pacific stations between midnight ET and 3am ET) could exclude trades the user expects to see.

3. **The CLI parser's "PM time" heuristic.** Should ideally compare the parsed time as a real datetime vs sunrise, not a string substring check. Probably fine in practice.

4. **The early-exit Kalshi snapshot changes** (commit 81ceca1). Made the Kalshi puller call `early_exits.process_early_exits` after writing snapshots, with the timer at 30s. Could be misfiring or eating into Kalshi's rate budget more than estimated. Independent of the dashboard issue but worth a check on `journalctl -u weatherbot-job@pull_kalshi_markets.service --since '1 hour ago'`.

5. **The settled-pull timer ordering.** It fires at 15:00 UTC, *after* settle at 14:23 UTC. If the intent was for settle to use Kalshi's value, this is the wrong order. As built, the Kalshi value is for dashboard display only.

## 7. Useful state queries

```sql
-- Settled fills per day (sanity check P&L numbers)
SELECT km.valid_date,
       count(*) as fills,
       sum(CASE WHEN pf.payout > 0 OR pf.exit_price > pf.price THEN 1 ELSE 0 END) as wins,
       round(sum(CASE WHEN pf.exit_price IS NOT NULL
                       THEN (pf.exit_price - pf.price)*pf.contracts - pf.fees - COALESCE(pf.exit_fees,0)
                       ELSE (pf.payout - pf.price)*pf.contracts - pf.fees END)::numeric, 2) as net_pnl
FROM paper_fill pf JOIN kalshi_market km ON km.ticker=pf.ticker
WHERE km.valid_date >= '2026-05-20'
  AND (pf.payout IS NOT NULL OR pf.exit_price IS NOT NULL)
GROUP BY 1 ORDER BY 1 DESC;
```

```sql

SELECT station, local_date, tmax_f, tmax_time_lst, section
```
